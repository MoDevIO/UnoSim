## Rule 1: Regex statt String-Literal für Code-Analyse

### ❌ FALSCH
```typescript
const code = await page.locator(".monaco-editor").innerText();
expect(code).toContain("pinMode(13, OUTPUT)");
```

**Problem:** Monaco Editor rendert oft zusätzliche Whitespace-Marker, Zeilennummern, oder verwendet Variablen:
```
const int ledPin = 13;
...
pinMode(ledPin, OUTPUT);
```

### ✅ RICHTIG
```typescript
const code = await page.locator(".monaco-editor").innerText();
// Flexibel gegenüber Whitespace, Variablen, Zeilenumbrüchen
expect(code).toMatch(/pinMode\s*\(\s*(?:13|ledPin)\s*,\s*OUTPUT\s*\)/);
```

Oder noch besser - Monaco API nutzen:
```typescript
const code = await page.evaluate(() => {
  return (window as any).monaco?.editor?.getModels?.[0]?.getValue() || "";
});
expect(code).toMatch(/pinMode\s*\(\s*(?:13|ledPin)\s*,\s*OUTPUT\s*\)/);
```

## Rule 2: Variablen-Logik bei der Verifikation

### ❌ FALSCH
```typescript
expect(code).toContain("digitalWrite(13, HIGH)");
```

### ✅ RICHTIG
```typescript
// Prüfe Variablendefinition UND Verwendung
const varMatch = code.match(/const\s+(?:int\s+)?(\w+Pin)\s*=\s*13/);
const pinVar = varMatch?.[1] || "13";
expect(code).toMatch(new RegExp(`digitalWrite\\s*\\(\\s*${pinVar}\\s*,\\s*HIGH\\s*\\)`));
```

## Rule 3: Monaco API statt DOM-Scraping

### ❌ FALSCH (DOM-Scraping)
```typescript
const text = await page.locator(".monaco-editor").innerText();
const lines = text.split("\n");
const codeLines = lines.filter(l => !l.match(/^\d+/)); // Zeilennummern filtern
```

### ✅ RICHTIG (Monaco API)
```typescript
const code = await page.evaluate(() => {
  const editor = (window as any).monaco?.editor;
  if (!editor) return null;
  const model = editor.getModels?.()[0];
  return model?.getValue?.() || null;
});

expect(code).toMatch(/your-regex-here/);
```

## Rule 4: Fehlertoleranz und Robustheit

### ❌ FALSCH
```typescript
const pin13Frame = page.locator('[data-pin="13"]');
await expect(pin13Frame).toBeVisible({ timeout: 5000 });
```

Wird fehlschlagen wenn:
- Element später rendert (Race Condition)
- Andere Tests nicht isoliert sind
- WebSocket nicht rechtzeitig verbunden

### ✅ RICHTIG
```typescript
// 1. Test-Isolation mit testRunId
const testRunId = `test-${Date.now()}-${Math.random().toString(36).substr(2, 9)}`;
await page.addInitScript((id: string) => {
  window.sessionStorage.setItem("__TEST_RUN_ID__", id);
}, testRunId);

// 2. Backend Reset vor jedem Test
await page.context().request.post("/api/test-reset");

// 3. Größeres Timeout + Retry-Logik
for (let attempt = 0; attempt < 3; attempt++) {
  try {
    await expect(pin13Frame).toBeVisible({ timeout: 15000 });
    break;
  } catch (e) {
    if (attempt === 2) throw e;
    console.log(`Attempt ${attempt + 1} failed, retrying...`);
    await page.waitForTimeout(1000);
  }
}

// 4. Debug-Info bei Fehler
if (!(await pin13Frame.isVisible())) {
  const allPins = await page.locator('[data-pin]').evaluateAll(els =>
    els.map(el => el.getAttribute('data-pin'))
  );
  console.log(`Available pins: ${allPins.join(", ")}`);
  await page.screenshot({ path: "debug-pins.png" });
}
```

## Rule 5: WebSocket-Isolation für parallele Tests

### ✅ IMPLEMENTIERT
```typescript
// Backend: server/routes.ts
const testRunId = req.query.testRunId as string;
ws.testRunId = testRunId; // Jeder Client bekommt unique testRunId

// Frontend: client/src/hooks/use-websocket.ts
const params = new URLSearchParams({
  testRunId: window.sessionStorage.getItem("__TEST_RUN_ID__") || ""
});
const ws = new WebSocket(`ws://localhost:3000?${params}`);
```

Dies verhindert State-Bleed zwischen Tests, auch wenn sie parallel laufen.

## Rule 6: Store-Reset für Test-Isolation

### ✅ IMPLEMENTIERT
```typescript
// Preserve pin states, nur Events clearing
resetToInitial: () => {
  pendingEvents.clear(); // ← Events weg
  // pinStates bleiben erhalten! ← Wichtig
  notify();
}

// Für Hard-Reset (wenn nötig):
resetToEmpty: () => {
  pendingEvents.clear();
  snapshot = initialSnapshot; // ← States auch weg
  notify();
}
```

**Warum:** Tests brauchen die aktuell-geladenen Pin-States, aber nicht alte Event-Daten.

## Checkliste für neue Tests

- [ ] `test.beforeEach`: Unique `testRunId` + Backend Reset
- [ ] Monaco API für Code-Analyse verwenden (nicht DOM-scraping)
- [ ] Regex für flexible String-Matching verwenden
- [ ] Variablenlogik beachten (z.B. `const ledPin = 13; pinMode(ledPin, ...)`)
- [ ] `toMatch()` statt `toContain()` für Code
- [ ] WebSocket-Timeout: mindestens 1000ms nach Navigation
- [ ] Simulation-Start: zusätzliche 2000ms Wartezeit für Registry-Collection
- [ ] Error-Handler: Screenshots + Variablen-Logging bei Fehlern
- [ ] Serial-Mode für Tests (keine parallelen Ausführungen)

## Typische Fehler und Lösungen

| Fehler | Ursache | Lösung |
|--------|--------|--------|
| `element(s) not found` | Race Condition bei Pin-Rendering | WebSocket-Timeout erhöhen, `startSimulation()` + 2s Wartezeit |
| `toContain()` schlägt fehl | Whitespace/Variablen in Monaco | `.toMatch(/regex/)`statt `.toContain()` |
| State-Bleed zwischen Tests | Fehlende Test-Isolation | `testRunId` in sessionStorage + `/api/test-reset` |
| WebSocket-Timeout | Zu schnelle Erwartungen | Backend: `await page.waitForTimeout(1000)` nach `.goto()` |
| Compiler-Fehler (`ld: open()`) | Temp-Directory-Cleanup fehlt | Server: `SandboxRunner` cleanup-Logic überprüfen |
